# ADR-004：并发是配置，不是平台前提

**状态：已采纳（2026-09-15）**

## 背景

早期实现把 ECNU 平台的串行建议编码为 `LLM_SERIAL_LLM` 和客户端闸门。这把部署策略误当成领域架构约束，也使并行数据采集和多用户扩展受限。

## 决策

`LLM_CONCURRENCY` 是唯一并发配置，默认值为 4；设置为 1 即获得串行语义。`ChatClient` 使用单一跨同步/异步调用的限流器，限流仅覆盖一次网络往返，重试在限流器外。业务层只依赖 LLM 端口与能力路由，不感知供应商或并发策略。

旧 `LLM_SERIAL_LLM` 兼容别名与客户端参数已在 B5-4 删除。

## 后果

- 部署可按账号限流、成本和机器容量调整并发，无须修改业务代码。
- CLI、API、照片工具共享由装配根注入的客户端边界；照片工具不再自行构造客户端。
- ADR-002 的平台中立性不变；平台特有扩展仍由适配层处理。

## 2026-10-06 实现核对与范围

上述配置机制继续适用；“已采纳”表示现有代码采用，本次未另行找到原始用户确认记录，不补造历史。默认4与设1串行一致，ECNU真实联调建议配置1。

设计约束不等于取消行为已验证正确：排队 acquire 经 to_thread，被取消后后台线程仍可取得许可而未释放，本次已离线重现；超时配置和重试总预算亦有缺口。详见 [审查A04](../AUDIT-2026-10-06.md)。修复实现，不据此改掉唯一并发配置或引入多智能体。

## 2026-10-06 U2-1 修复核对

本节记录上述审查之后的实现修复，不补造新的产品或架构批准。限流器仍只有一个跨同步/异步的 BoundedSemaphore；异步排队改为非阻塞获取与可取消等待，取消不遗留 acquire 线程，不承诺 FIFO。每个事件循环缓存自己的 SDK HTTP 连接池，共享同一客户端门面和限流器，避免跨 loop 复用绑定连接。

LLM_TIMEOUT 实际传入 SDK/httpx；SDK max_retries=0，外层总尝试上限3（首次+2次重试），退避在许可之外。阶段超时不是整条管线截止时间。重复取消、超时/异常、同步异步共享、SDK底层计数及本地HTTP超时离线通过；浏览器停止等待不能确认已运行线程或供应商请求取消。详情见 [U2-1 验收记录](../audit/2026-10-06/u2-1-verification.md)。LLM_CONCURRENCY 仍为唯一并发配置。

## 2026-10-09 SDK 生命周期修复核对

按本人本批授权修复现有实现，不新增并发配置或另行补造架构批准。Runtime同步门面原先逐次asyncio.run，销毁了SDK缓存池的所属循环；本机真实keepalive经生产路径复现保存后Event loop is closed。Runtime与SDK同步门面现共用infra.async_runner的持久执行器，连接池仍按loop隔离并共享唯一限流器；异步宿主必须在自己的loop停止前关闭自建资源。

aclose只在每个池的所属loop关闭，停止的loop不跨循环兜底；失败过滤凭据并显式报告、保留句柄，成功才移除。清理锁只保护资源释放，不修改请求许可、重试、超时或输出上限。进程级共享循环不随单个应用关闭，应用只释放自建池，注入资源仍归注入方。新增keepalive9、全量640及相关护栏通过，真实外调0；范围、复现与未验证边界见[SDK验收](../audit/2026-10-09/u4-sdk-lifecycle-verification.md)。
