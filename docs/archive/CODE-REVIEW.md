# LightTrail 审查标准

> 修订：2026-10-06。以用户影响、可复现证据和当前入口判定；不把文档中的硬措辞当用户批准证明。保留原六维检查与历史回归点的目的，调整过度机械的流程。

## 1. 发现格式与级别

每条写明：基线、文件/行号、触发条件、实际/期望、影响、证据等级（运行/静态/历史/未验证）、修复方向和验收。先独立审查，再复核既有报告，标成立、部分、已修复或证据不足。

| 级别 | 判断 |
|---|---|
| P0 | 直接破坏本次核心用户判断、可能造成错误行动，必须先修；例如失败数据成为可信出发依据 |
| P1 | 重要正确性、死锁、数据/隐私或交付故障；注明本地或公开部署触发条件 |
| P2 | 可维护性、文档与优化；按影响排期，不以行数或偏好充当阻断 |

未提交改动本身不等于安全或功能故障；先保护原件、检查diff与来源。重复代码、版本号不同、预留接口和设计分歧需证明影响。真实缺陷不因“仅本地单用户”而一概降级。

## 2. 六维检查

- 正确性：时区/目标日期/新鲜度、空值与合法0、短快门/单位、极端天文事件部分缺失；前置检查先于昂贵调用。
- 安全隐私：用户路径与身份来源分开；Origin/Host及写接口；密钥repr/异常/日志；照片/EXIF/坐标外传、文件权限、删除与撤回；上传限额在读入前或分块执行。
- 可维护性：职责清楚，有限提取重复；遗留TODO与文档承诺核对；遵守AGENTS风格。不要为固定80行/两份重复自动重构。
- 架构契约：生产装配与测试替身路径对照；预留端口标清；API响应/事件契约经OpenAPI生成；新架构决策有来源。已采用ADR遵循其实际适用范围，不扩大到禁止器材品牌等无关规则。
- 测试：断言实际地点/日期/题材与数据资格；构造失败工具+恶意模型输出、取消等待、恢复过期和跨用户等反例；记录真实与合成的区别。
- 文档：需求/现状/执行各有唯一职责；当前架构不写目标已实现；研究宣传不是精度验证；历史确认无法找到就标缺证据，不补造批准。

## 3. 工作流程与验证

先列范围并保护未提交内容 → 独立检查 → 运行与改动相关的门禁 → 复核旧AI发现 → 修正/记录 → 复验并报告限制。

编码批次收口通常需要pytest、Ruff、smoke、lint-imports；涉及API/前端再做契约与build/相关浏览器检查。纯文档改动核对链接、编号、职责与原件，不机械重跑无关服务；完整工程回归只在范围/风险需要时执行。归档原件不可为格式门禁改写，明确排除范围并记录已知差异。

独立视角有价值，但不强制每次创建新代理；是否委派遵循用户和当前环境授权。不能以审查标准推导自动push/PR/发布，也不强制将其他人的未提交内容commit。批次结果记录devlog，遗留项进入唯一路线图。

## 6. 回归清单（历史已修复缺陷，审查时逐项核对）

| 缺陷 | 修复批次 | 回归检查点 |
|---|---|---|
| SessionManager 死锁（持锁调 save） | B0-1 | 锁内只改内存；落盘/淘汰持久化在锁外 |
| `get()` 返回共享可变 record | B0-1 | 深拷贝返回，改动经 `save()` 生效 |
| 工具层反向依赖 orchestrator/registry | B0 | `tools/` 无 upward import（lint-imports + AST） |
| 前端 D3 硬映射置信度、正则猜结论 | R0-6 | D3 渲染来自结构化 card 字段 |
| D2 用正则解析工具 JSON | S1-4 | D2 只消费 OpenAPI 生成的结构化类型 |
| `/api/decide` 旁路 Orchestrator.plan | R0-2 | Web 决策必经统一规划入口 |
| 照片链路读旧路径 profile.json | R0-4 | 器材从当前请求用户档案读取 |
| 相对日期全解析为明天 | R0-5 | 跨周/周末/ISO 日期各有测试 |
| D4 固定 outcome=success | R0-6 | 结果由用户选择，未选不写事件 |
| 依赖声明不一致（fastapi 缺失等） | R0-8 | `pyproject.toml` 为真源，requirements 仅兼容清单 |



## 7. 新增故障类

- 高可靠工具失败时不能继续按默认high；模型依据必须对账真实事实。
- 等待Semaphore的协程取消后，后台线程不得吞掉许可。
- 旧卡/冻结回放/实时重查有明确日期与版本；恢复ID不等于恢复内容。
- 数据缺失与0区分；时效比较完整绝对时刻；相机库必须从生产装配验证。
- 工程/合成/真实服务/用户效果分开报；不从用例数量推导完成率。
