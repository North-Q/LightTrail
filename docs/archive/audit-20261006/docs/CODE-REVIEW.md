# LightTrail 代码审查标准与流程

**版本**：v1.0
**建立日期**：2026-10-03
**适用对象**：为 LightTrail 编码的 Agent（含审查代理）与小北（人工抽查与拍板）
**定位**：本文定义光迹的代码审查分级标准、检查清单、审查流程与产出规范。它是 `AGENTS.md` 工程约束的执行细化，不改变 `docs/AGENT-ROADMAP.md` 的任务优先级与批次闸门。

---

## 1. 为什么需要系统化审查

光迹的规模已经超过「一个人能在脑中保持全部上下文」的阈值（src 约 1.5 万行、tests 约 9 千行、前端约 5.6 千行）。历史审计证明：分层成环、注释承诺大于实现、前端伪造数据、契约双份手写这类问题，靠开发时的自觉抓不住，必须靠**独立于编码者视角的第二双眼睛**在固定检查点系统性排查。

审查的三个目标（按优先级）：

1. **防回退**：不让已修复的缺陷类（死锁、路径穿越、用户串读、前端硬映射）以新面貌回归；
2. **防漂移**：代码、注释、文档、OpenAPI 契约四处声明与实现保持一致；
3. **传知识**：每次审查的发现沉淀为可复用规则，而不是一次性意见。

## 2. 严重级别定义

| 级别 | 定义 | 处理要求 |
|---|---|---|
| 🔴 **Blocker** | 正确性错误、安全漏洞、数据丢失/损坏风险、竞态或死锁、契约破裂、违反已拍板 ADR 或分层门禁 | 修复合并前不得通过；批次收口时存在未处理的 🔴 则批次不算完成 |
| 🟡 **Suggestion** | 应修复：输入校验缺失、覆盖缺口、资源浪费、可维护性债（重复样板、超长函数）、注释与实现不符 | 必须记录并排期（进路线图或本批遗留清单）；连续两个批次不处理需向小北说明理由 |
| 💭 **Nit** | 风格不一致、命名改进、文档小缺口、值得考虑的替代方案 | 记录即可，不强制；攒够一批同类可合并成一个 🟡 |

**判定规则**：

- 「本地单用户阶段可容忍、公网部署前必须修」的项标 🟡，但必须在条目上注明 **「P1 前置」**，进 `docs/AGENT-ROADMAP.md` P1 批次的输入清单；
- 不确定是 🔴 还是 🟡 时，看后果：**不可逆**（数据丢失、安全、死锁）→ 🔴；可逆（浪费、体验、债）→ 🟡；
- 审查者存疑时**提问题而不是断言错误**——标 ❓ 附在发现里，由编码方澄清意图。

## 3. 六维检查清单

以下清单按光迹的技术形态定制。每项检查都可追溯到历史真实缺陷或本仓结构性风险，不是通用模板。

### 3.1 正确性

- [ ] 数值与天文/曝光计算：500/NPF 法则、ND 档位、EV 等效换算的数学正确性；除零、负数、极端纬度等边界有处理或显式报错；
- [ ] 相对日期解析基于请求时区与请求时刻（R0-5 修复项，防「后天→明天」回归）；
- [ ] 异常路径真的可达且被测试覆盖，而不是 `except: pass` 或只写不测；
- [ ] 业务性降级与故障性降级可区分（例如「路由置信度低」不应伪装成 `ValueError` 混入管线故障）；
- [ ] 资源使用顺序合理：**先检查前置条件，再做昂贵调用**（多模态/外部 API 调用前先校验本地数据可用性）；
- [ ] Windows 兼容：文件替换竞态、路径分隔符、临时目录权限（本仓主开发环境是 Windows）。

### 3.2 安全与隐私

- [ ] 用户输入拼进 SQL（FTS5 查询词）、文件路径（session_id/user_id/spot_id）、shell 时必须走参数化或白名单校验；
- [ ] `user_id` 从 `RequestContext` 贯穿到文件系统与 SQLite，无旁路读取其他用户目录的路径；
- [ ] 密钥（`api_key` / `amap_*` / `baidu_map_ak`）不进日志、trace、异常消息、repr；新增密钥字段一律 `repr=False`；
- [ ] 坐标、EXIF、照片的流向符合路线图隐私决策：默认导出不含结构化经纬度；临时文件用后即删；
- [ ] 文件上传：类型与大小校验在**读入内存之前**或流式进行（防超大文件先占内存）；
- [ ] 地图代理保持本机同源限制（`_require_local_map_request` 的三个检查不被新端点绕过）；
- [ ] CORS、认证边界的状态与 `docs/architecture.md`「已知接线缺口」声明一致，不出现文档未记录的放宽。

### 3.3 可维护性

- [ ] 注释与 docstring 承诺的功能在代码中真实存在（本仓历史雷区：缓存承诺、tokens 统计、时效计算都曾「注释说了代码没做」）；
- [ ] 无重复样板：相同形态的端点/函数超过 2 份即应提取工厂或公共实现；
- [ ] 超过 ~80 行的函数考虑拆分；模块级提示词常量集中管理；
- [ ] `type: ignore` 必须带注释说明原因，且不得用来掩盖契约设计缺陷（如「必填字段恒传 None」应改契约为 Optional）；
- [ ] 命名与项目约定一致：中文工具返回字段、常量大写下划线、私有前缀下划线、日志 `%` 占位符；
- [ ] 装配纪律：`composition.py` 之外的模块不得出现跨层 `new`；测试替身只经 `build_application` 的注入点进入。

### 3.4 架构与契约

- [ ] 分层门禁三件套全绿：`lint-imports`（3 kept / 0 broken）+ `tests/test_architecture.py` AST 检查 + 品牌字面量检查；
- [ ] 契约单一真源：前后端共享类型只经 `OpenAPI → npm run gen:api` 生成；**禁止**在前端手写与后端平行的契约文件或用正则解析后端 JSON；
- [ ] 新增 API 端点必须有 `response_model`（Pydantic 契约进 OpenAPI components）；裸 `dict` 返回值视为契约缺口；
- [ ] 模型选择只经 `ModelRouter`，业务代码出现模型品牌字面量即 🔴（ADR-002）；
- [ ] 历史已修复缺陷不回归：SessionManager 锁语义、`PUT /api/profile` 不写机位、D4 唯一事件入口等（见 §6 回归清单）。

### 3.5 测试

- [ ] 新增工具/管线/端点配测试：正常、边界、降级、用户隔离四类各有覆盖（路线图统一完成定义第 3 条）；
- [ ] 断言断**具体值与语义**（地点、绝对日期、题材），不断「不抛异常」；文案像答案不等于通过（R0-7 原则）；
- [ ] 反例测试存在：构造「问 A 答 B」必须失败的用例，防止评估只会放行；
- [ ] 测试间无共享可变状态；临时目录用例级隔离并清理；
- [ ] 替身（Fake/cassette）模拟的是**生产装配路径**，而不是绕过装配根的自造捷径。

### 3.6 文档一致性

- [ ] `README` 只描述已验证能力，区分稳定/实验/规划；
- [ ] `docs/architecture.md` 的「已知接线缺口」与代码现状同步：新接线完成时缺口条目同步删除；
- [ ] devlog 条目含验证证据（pytest 数、哈希、闸门状态）；
- [ ] ADR 引用链完整：`Supersedes` 指向的 ADR 必须存在于 `docs/adr/` 或有明确去向说明；
- [ ] 版本号一致：`pyproject.toml`、FastAPI app 版本、README 状态描述不互相矛盾。

## 4. 审查流程

光迹是「Agent 编码 + 批次闸门」的单人项目，审查嵌入三个固定检查点，不引入大厂式 PR 多人评审。

### 4.1 批次内自检（每个原子任务完成时，编码 Agent 执行）

1. 对照 §3 清单中与本次改动相关的维度自查；
2. 跑工程门禁五连：`pytest -q` / `ruff check .` / `python -m lighttrail.smoke` / `lint-imports` /（涉前端时）`gen:api + build`；
3. 自查发现的 🔴 当场修复；🟡 记入本批遗留清单；
4. devlog 记录中写明「自检发现与处置」一行。

### 4.2 批次收口审查（闸门停下时，独立审查 Agent 执行）

1. **独立性要求**：审查者不得是本批编码者（小北单人项目下即「新会话/新代理」，不带本批实现的记忆）；
2. 范围：本批全部改动（`git diff` 范围）+ §3 全量清单 + §6 回归清单；
3. 产出《批次审查报告》：分级发现列表（文件:行号 + 问题 + 建议）、门禁结果复核、遗留风险；
4. 闭环：🔴 全部处理且复验通过 → 闸门可宣布通过；🟡 形成遗留清单进 devlog；
5. **commit 纪律**：批次审查通过后必须 commit（本地 commit 无需授权；push/PR 仍按小北拍板规则）。工作区长期挂数千行未提交改动本身记 🔴——版本控制是唯一可靠的回滚点。

### 4.3 专项全面审查（阶段性，小北发起或路线图批次间隙）

- 范围：全仓（src + tests + frontend + evals + docs），按 §3 六维全查；
- 方法：分层分派并行细读（核心架构文件人工细读，外围层可分派只读探查代理），发现必须给行号级证据；
- 产出：综合审查报告 + 更新本标准（把新发现的缺陷类沉淀进 §3/§6）；
- 频率参考：每完成一个大批次（如 R0、S1、D1 级别）或累计改动超 ~3000 行时一次。

### 4.4 发现的处理闭环

```
发现（分级+行号+证据）→ 编码方确认/反驳（存疑项澄清意图）→ 修复 → 复验（针对性测试 + 门禁）
→ 记录（devlog；🔴/🟡 归档进回归清单 §6）
```

## 5. 审查产出规范

每份审查报告必须包含：

1. **基线声明**：审查对象的 commit/工作区状态、代码规模、审查日期；
2. **发现列表**：按 🔴 → 🟡 → 💭 排序，每条含 `文件路径:行号`、问题描述（引用代码）、影响分析、修复建议；
3. **亮点**：值得保留和推广的模式（审查不止挑错，好模式需要正反馈才会被复用）；
4. **统计**：各级别数量 + 与上次审查的对比（趋势）；
5. **门禁复核**：pytest/ruff/smoke/lint-imports/OpenAPI 哈希的实际运行结果，不采信口头声明。

## 6. 回归清单（历史已修复缺陷，审查时逐项核对）

| 缺陷 | 修复批次 | 回归检查点 |
|---|---|---|
| SessionManager 死锁（持锁调 save） | B0-1 | 锁内只改内存；落盘/淘汰持久化在锁外 |
| `get()` 返回共享可变 record | B0-1 | 深拷贝返回，改动经 `save()` 生效 |
| 工具层反向依赖 orchestrator/registry | B0 | `tools/` 无 upward import（lint-imports + AST） |
| 前端 D3 硬映射置信度、正则猜结论 | R0-6 | D3 渲染来自结构化 card 字段 |
| D2 用正则解析工具 JSON | S1-4 | D2 只消费 OpenAPI 生成的结构化类型 |
| `/api/decide` 旁路 Orchestrator.plan | R0-2 | Web 决策必经统一规划入口 |
| 照片链路读旧路径 profile.json | R0-4 | 器材从当前请求用户档案读取 |
| 相对日期全解析为明天 | R0-5 | 跨周/周末/ISO 日期各有测试 |
| D4 固定 outcome=success | R0-6 | 结果由用户选择，未选不写事件 |
| 依赖声明不一致（fastapi 缺失等） | R0-8 | `pyproject.toml` 为真源，requirements 仅兼容清单 |

## 7. 与既有工程体系的衔接

| 既有机制 | 审查标准的关系 |
|---|---|
| `AGENTS.md` 代码风格节 | §3.3 引用其约定，不重复定义 |
| 路线图「统一完成定义」9 条 | §4.1 自检即其第 3/4 条的执行化 |
| 批次闸门（§4.2） | 收口审查是闸门「停下汇报」的前置动作 |
| 工程门禁五连 | 机械可查项交给工具；审查聚焦工具抓不住的语义/结构问题 |
| devlog | 审查报告的结论性条目（遗留清单、回归项）归档进 devlog 对应批次 |
| ADR | 违反已拍板 ADR 直接 🔴；新 ADR 落地后其要点进 §3.4 |

## 8. 维护

- 本标准由专项全面审查（§4.3）负责更新：新缺陷类沉淀进 §3/§6，过时规则删除；
- 版本号递增：小修 v1.x，结构性调整升 v2；
- 修改本文件不需要小北逐字确认，但结构性调整（分级定义、流程变更）需在汇报中明示。
