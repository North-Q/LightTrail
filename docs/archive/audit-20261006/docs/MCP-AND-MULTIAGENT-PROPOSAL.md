# LightTrail MCP 与多智能体结合方案（开发建议）

> **文档版本**：v1.0
> **日期**：2026-10-05
> **文档性质**：**开发建议**，供小北决策。本文提出的方向在获得批准前不构成开发指令。
> **冲突处理**：本文与 `docs/AGENT-ROADMAP.md` 冲突时，以路线图为准。批准后的条目由路线图负责编排执行顺序。
> **前置阅读**：`docs/AGENT-ROADMAP.md`、`docs/architecture.md`、`docs/adr/`、`AGENTS.md`

---

## 0. 一句话结论

光迹当前 15 个声明式工具已经具备 `ToolSpec` 自描述（`description` + JSON Schema `parameters` + `capabilities`），**与 MCP 协议的工具定义几乎一一对应**，因此：

- **MCP Server（方向①）** 是"补齐就该有"的能力分发层，工作量约 1 天，风险极低，收益最高。
- **MCP Client（方向②）** 用于兑现"工具热插拔"承诺，并可与 O1-4 的外部数据源可行性评估合并为同一件事。
- **多智能体（方向③④）** 只在两个具备**明确的上下文隔离理由**或**对抗式归因需求**的位置引入；**不做为简历堆砌的通用多 Agent 改造**。

## 1. 背景与动机

### 1.1 现状盘点（2026-10-05 实测）

| 项 | 数值 |
|---|---|
| 后端 | 83 个 `.py` / 15339 行 |
| 测试 | 58 文件 / 10080 行 / pytest 收集 **458 用例** |
| 前端 | 31 个 ts/tsx / 5785 行 |
| evals | 1607 行 |
| git | main 分支 / 171 commits / HEAD `4b04b81` |
| 工具 | 15 个声明式 `ToolSpec`（astronomy 5 / exposure 3 / weather 2 / photo_analysis 2 / basic 1 / memory 1 / site_match 1） |
| ADR | ADR-002 平台中立 / ADR-003 reason 扩展参数 / ADR-004 并发即配置 |

### 1.2 动机

1. **求职维度**：MCP 是当前 Agent 岗位 JD 的高频关键词；光迹 15 个工具已具备暴露条件，属于低成本高命中投入。
2. **产品维度**：光迹当前唯一入口是 Web 应用，用户必须"专程访问"。MCP 化后能力可被任意支持 MCP 的客户端调用，获取成本从"部署应用"降到"加一段配置"。
3. **架构维度**：`ToolRegistry` 目前只能装载代码内声明的工具，"热插拔"是**对内成立、对外不成立**的承诺。MCP Client 可真正兑现该承诺。
4. **数据维度**：光迹最大短板是**缺少量化指标**。方向③④天然产出 token 数、延迟、归因准确率等可测量数据。

## 2. 方向①：MCP Server（对外暴露 15 个工具）

### 2.1 目标

在**不改动任何现有领域工具**的前提下，新增 MCP Server 适配层，把 `ToolRegistry` 中的 15 个工具通过 MCP 协议对外提供 `tools/list` 与 `tools/call`。

### 2.2 字段映射分析

`ToolSpec`（`src/lighttrail/contracts/tool.py`）与 MCP Tool 定义高度同构：

| ToolSpec 字段 | MCP 对应 | 说明 |
|---|---|---|
| `name` | `tools[].name` | 语义一致（OpenAI function name，全局唯一） |
| `description` | `tools[].description` | 一致；光迹额外要求"何时使用" |
| `parameters` | `tools[].inputSchema` | 均为 JSON Schema；MCP 要求顶层含 `"type": "object"` |
| `capabilities` | 无直接对应 | 光迹增量（供 ModelRouter 路由）；可映射到 `annotations` |
| `main_field` | 不暴露 | 光迹可解释性内部字段 |
| `confidence` / `confidence_rule` | 不暴露 | 光迹置信度内部字段 |

结论：**转换逻辑几乎只是字段重命名 + 顶层类型补全**，无需改动领域工具。

### 2.3 关键技术决策：上下文如何跨越进程边界

现有工具签名为 `__call__(ctx: ToolContext, **kwargs)`，其中 `ToolContext` 携带：

- `request: RequestContext`（含 `user_id`，记忆隔离依据）
- `llm` / `datasource` / `memory` / `knowledge` / `sink` 五个注入端口

**MCP 协议无"上下文"概念**，只有 `tools/call(name, arguments)`。三种可选设计：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A. 参数透传 | `user_id` 放入 arguments | 简单、无状态、可水平扩展 | 污染工具签名，模型可能填错 |
| B. Session 绑定 | 连接建立时绑定身份，服务端持有会话 | 工具签名干净 | 有状态，需会话管理 |
| C. 双模式适配 | 本地直调走 `ToolContext`；MCP 侧用 A/B 包一层 | 现有代码零改动，纪律不破 | 需一层适配代码 |

**建议采用 C + A 组合**：新增 `src/lighttrail/mcp/` 包做适配；领域工具与契约层均不修改；`user_id` 经 MCP `_meta` 或 arguments 传入并在服务端校验。

### 2.4 安全约束（必须在实现中满足）

- **身份来源必须校验**：不得无条件信任客户端传入的 `user_id`；本地单用户场景默认映射到 `_local`，多用户须先完成 P1 的认证收口。
- **`memory_tool` 与 `photo_analysis` 的暴露需单独评审**：前者读取用户档案，后者处理用户照片。在无认证的前提下，默认**不暴露**这两类工具，或以显式开关控制。
- **只读优先**：优先暴露纯计算与只读工具（天文、曝光、天气、机位匹配）；写状态类工具需显式标注。

### 2.5 验收标准

1. MCP Client 可成功 `tools/list`，返回工具数与 `ToolRegistry` 一致，schema 无漂移。
2. 至少 3 个纯计算工具（如 `sun_times` / `equivalent_exposure` / `star_shutter_rule`）可成功 `tools/call` 并返回正确结果。
3. 新增离线测试：`ToolSpec` → MCP Tool 转换的字段一致性断言。
4. `smoke.py` 增加 MCP 层检查项（工具可列举、schema 与注册表一致）。
5. 不修改 `contracts/`、`domain/`、`tools/` 中任何领域文件（由 `import-linter` 与代码审查确认）。

### 2.6 非范围

- 不做远程部署、鉴权服务、多租户隔离（属 P1）。
- 不改动 15 个领域工具的实现。
- 不引入 HTTP/SSE 之外的 MCP 传输方式（stdio 优先）。

## 3. 方向②：MCP Client（挂载外部 Server，兑现热插拔）

### 3.1 目标

让 `ToolRegistry` 除静态工具外，还能在运行时装载来自外部 MCP Server 的工具，使"新增工具"从"改代码 + 重新部署"变为"加一行配置"。

### 3.2 现状问题

`tools/__init__.py` 的注释声明"新增工具 = 在此追加一行"，该口径**对项目内部成立，对外部开发者不成立**：外部贡献者必须 fork、写模块、改收集点元组、重新打包。这构成"热插拔"承诺与实现之间的落差。

### 3.3 目标形态

```
ToolRegistry
  ├── 静态工具（内建 15 个，来自 TOOLS 元组）
  └── 动态工具（来自 MCP Servers，运行时发现）   ← 新增
```

配置文件示例（`mcp_servers.json`）：

```json
{
  "servers": {
    "lightpollution": { "command": "uvx", "args": ["lightpollution-mcp"] },
    "tide": { "url": "https://example.invalid/mcp" }
  }
}
```

Client 连接后调 `tools/list`，把返回工具动态注册进 `ToolRegistry`；`ContextBuilder` 因从注册表生成工具层，模型看到的清单自动包含外部工具；trace 增加 `source: mcp/<server>` 标记。

### 3.4 关键设计点

| 议题 | 设计要点 |
|---|---|
| 命名冲突 | 外部工具名加命名空间前缀（如 `mcp__lightpollution__get_pollution`）；注册时校验与 `ToolSpec.name` 全局唯一约束不冲突 |
| 信任边界 | 外部 Server 属不可信代码；须限制其可访问的数据范围，且默认只接受只读工具 |
| 失败降级 | Server 超时/断连时，该工具标记为不可用并返回明确错误，不得静默失败；延续 `needs_data` 的诚实降级哲学 |
| 权限声明 | MCP `annotations`（如 `readOnlyHint`）映射到光迹 `Confidence` 档位：只读数据源 `HIGH`，有状态写入 `MEDIUM` |
| 可观测性 | 外部工具调用进入 `TraceRecorder`，与内建工具使用同一套主字段与来源标注 |

### 3.5 与 O1-4 的合并机会

路线图 O1-4 要求对"光污染、云层光路、潮汐"等候选外部数据源做可行性 spike（记录许可、成本、覆盖、更新频率、缓存策略、失败降级）。**该需求与本方向同构**：

> 把每个候选数据源先包成 MCP Server，评估期挂载、不达标即摘除，主链路零污染。

**建议：O1-4 的 spike 直接以 MCP Client 为实现载体**，可减少一次重复建设。

### 3.6 验收标准

1. 配置文件可声明至少 2 个外部 Server；启动后工具总数 = 内建数 + 外部可用数。
2. 外部 Server 不可用时，启动不失败，且该工具在 trace 中标记为不可用并给出原因。
3. 命名冲突场景有明确报错，不产生静默覆盖。
4. 新增测试覆盖：动态注册、命名冲突、Server 无响应降级、外部工具 trace 来源标注。
5. 提供一份 `mcp_servers.json.example` 与 README 使用说明。

### 3.7 非范围

- 不做 MCP Server 市场、自动发现、版本协商。
- 不允许外部工具写入用户记忆（安全边界，需单独评审）。

## 4. 方向③：D2 多机位赶场 → 真并行子代理

### 4.1 目标

在 O1 多机位时空编排中，把"并行取数"升级为"每个机位独立上下文的并行推理"，并**产出可测量的上下文工程指标**。

### 4.2 现状与问题

当前 `orchestrator/pipelines.py` 的 `_collect_async` 使用 `asyncio.TaskGroup` 并行**取数**（IO），取数结果全部汇入**同一上下文**做一次综合。多机位场景下该设计存在三个问题：

1. **注意力稀释**：4 个机位的天气/天文/机位数据混在同一 prompt，易发生字段错配（R0-5 已在修单机位的地点错配，多机位下风险放大）。
2. **上下文压力**：单次 `weather_forecast` 返回量可观，4 个机位叠加记忆注入、知识检索与工具 schema，易触及窗口上限。
3. **无法对等比较**：单次综合输出"选机位 A"，难以给出每个机位各自完整的判断依据与风险。

### 4.3 目标形态

```
                    ┌─ 子代理 A ─ 仅 A 的上下文 ─→ A 的独立判断 + 风险
主调度 Agent ───────┼─ 子代理 B ─ 仅 B 的上下文 ─→ B 的独立判断 + 风险
（只做编排与裁决）  ├─ 子代理 C ─ 仅 C 的上下文 ─→ C 的独立判断 + 风险
                    └─ 子代理 D ─ 仅 D 的上下文 ─→ D 的独立判断 + 风险
                              ↓
                    裁决：比较 N 份判断 → 输出取舍理由
```

### 4.4 实现约束

- **落位在编排层**：新增 `orchestrator/subagents.py`（或等价物），不得污染 `runtime/`；`runtime → contracts` 的依赖纪律保持不变。
- **复用现有门面**：`AgentRuntime` 已是可实例化门面（非单例），子代理各自构造实例并注入独立的 `ToolContext`。
- **并发上限复用 `LLM_CONCURRENCY`**：该配置项即为此类 fan-out 场景设计（ADR-004），不新增并发配置项。
- **子代理不写记忆**：子代理只产出结构化判断，记忆写入仍由主链路按 E1-3 的二次确认规则处理。
- **上限约束**：机位数沿用 O1-3 的"最多 4 个"；子代理轮次须有硬上限。

### 4.5 预期产出指标（本方向的核心价值）

| 指标 | 对比方式 |
|---|---|
| 上下文 token 数 | 单上下文方案 vs 子代理方案 |
| 端到端延迟 | 同上 |
| 字段错配率 | 同一组固定样例下的错误计数 |
| 工具调用往返次数 | 同上 |

**这些指标同时补齐光迹当前"缺少量化数据"的短板。**

### 4.6 验收标准

1. 固定 4 机位样例下，子代理方案可输出 4 份独立判断 + 1 份裁决，且裁决包含舍弃某机位的理由。
2. 上下文 token 数与延迟有可复现的对比数据，写入 devlog 或独立实验记录。
3. 单个子代理失败时，主调度可降级（输出其余机位判断并标注缺失），不整体失败。
4. 新增测试：子代理上下文隔离、并发上限生效、单子代理失败降级。
5. `import-linter` 契约无新增违反。

### 4.7 非范围

- 不做子代理之间的自由对话或多轮协商（那是方向④的领域）。
- 不引入新的 Agent 框架（沿用 PydanticAI）。
- 不改变 O1 已定的调度领域语义。

## 5. 方向④：D4 复盘 → 双角色对抗（推荐度最高）

### 5.1 目标

在 D4 复盘中引入**对抗式归因**：由持有不同信息的两方（规划师 / 摄影师）对质，再由中立的提炼者定位偏差根因，产出结构化 `AttributionCard`。

### 5.2 问题：单 Agent 复盘的"自圆其说"

当前复盘链路为「读取 EXIF + 比对计划 → 由 LLM 总结教训」。同一 LLM 同时看到"原计划的建议"与"实际拍摄结果"，倾向输出两边都成立的解释，例如：

> "虽然实际拍摄位置与原计划不同，但西侧视角同样捕捉到了良好的光线层次……"

此类输出**信息量为零**，因为该 Agent 的任务是"总结"而非"问责"。

### 5.3 目标形态

| 角色 | 角色设定 | 可见信息 |
|---|---|---|
| **规划师** | 曾给出建议，需捍卫判断依据 | 原 `SpotPlan` + 当时的天气/天文数据 |
| **摄影师** | 实际到场拍摄，知道现场实况 | 实际 EXIF + 复盘输入 + 实际时间 |
| **提炼者** | 不站边，定位偏差归因 | 双方陈述 + 计划/实际差异表 |

**核心机制**：信息不对称。规划师不知现场实况，摄影师不知数据依据，两者只能通过对质逼近真相。

示例对质：

> **规划师**：依据为 18:42 日落、东侧机位朝向 270°、云量 30%，属优质火烧云窗口。
> **摄影师**：18:30 到场，东侧机位被围挡占用，退至西侧；18:45 云确实烧了，但西侧被山体遮挡一半。
> **提炼者**：归因 = 机位可达性未核验（非天象误判）。教训：机位档案缺少"现场可达性"字段。→ 候选写入语义记忆

该结论是单 Agent 难以产出的，因为它需要"未看现场者"提出质疑、"未看数据者"给出反证，才能定位到"缺可达性字段"而非"火烧云预测不准"。

### 5.4 与现有能力的关系

- **方法论依据**：对抗式评审 / Red Team 思路在 Agent 中的应用，非自创花活，可清晰表述。
- **命中产品主线**：路线图 L3「计划—实际对比与经验提炼」与 A3 判断「只把稳定、可解释的结论写入语义记忆」。
- **叠加而非替换**：现有 `_diff_exif_vs_plan` 的**规则比对**保留，双角色在其之上增加**归因层**，延续"确定性 + 概率性"的分工（M1/M2 地基的延续）。
- **演示价值**：SSE 已能推送 trace，双角色对话可渲染为前端对话流，演示效果好。

### 5.5 实现约束

| 议题 | 约束 |
|---|---|
| 轮次上限 | 固定 2–3 轮对质 + 1 次归因，硬编码 `MAX_DEBATE_ROUNDS` |
| 输出契约 | 提炼者必须产出结构化 `AttributionCard { deviation, root_cause, category, memory_candidate }`，禁止自由文本 |
| 归因分类 | 必须是封闭集合（天象误判 / 机位问题 / 执行问题 / 天气突变 / 器材限制 / 其他），禁止模型自创类别 |
| 记忆写入 | 双角色最多产出"候选教训"，实际落库仍须用户二次确认（遵循 E1-3） |
| 依赖前提 | **必须先完成 E1 CaptureEvent 闭环**，否则不存在"实际现场"可供对质 |
| 成本控制 | 3 个角色 × N 轮 = 多次 LLM 调用，须记录 token 与成本并设上限 |

### 5.6 验收标准

1. 至少 3 组真实或构造的"计划 vs 实际"样例可完整跑通对质并产出 `AttributionCard`。
2. 归因类别始终落在封闭集合内；对无法归因的样例输出"信息不足"而非编造。
3. 同一组样例下，双角色归因结果**优于**单 Agent 总结（以人工评审或 LLM-as-judge 对比记录）。
4. 候选教训进入记忆前必须经过用户确认路径。
5. 单次复盘的 token 消耗与延迟有记录，且设有上限保护。

### 5.7 非范围

- 不做多轮自由辩论（固定轮次）。
- 不让子角色直接写记忆。
- 不替换现有确定性差异比对。

## 6. 明确不做的事（补充约束）

在本文范围内，以下做法**明确禁止**：

- **不为简历堆砌多 Agent**：路线图第 3 节"不做多 Agent"的原则不变，本方案仅在方向③④两个**有明确技术理由**的位置引入，且须在 ADR 中记录理由。
- **不引入第二个 Agent 框架**：方向③④均基于现有 PydanticAI 与 `AgentRuntime`。
- **不改动 `contracts/` 的零依赖约束**：MCP 适配代码一律放在 `adapters/` 或新增 `mcp/` 包。
- **不在无认证前提下暴露用户数据类工具**：`memory_tool` / `photo_analysis` 的 MCP 暴露须待 P1 认证收口后单独评审。
- **不把 MCP 化宣传为功能替代**：对外表述须明确"Web 应用承载深度决策，MCP 承载能力分发"的定位差异。

## 7. 建议的执行顺序

| 顺序 | 方向 | 前置 | 预计工作量 | 建议理由 |
|---|---|---|---|---|
| 1 | ① MCP Server 暴露 15 工具 | 无 | 约 1 天 | 零依赖、零风险，可立即产出可演示成果 |
| 2 | ② MCP Client + 挂 1 个外部 Server | ① | 2–3 天 | 兑现热插拔承诺；与 O1-4 spike 合并可省一次建设 |
| 3 | ④ D4 双角色对抗 | E1 闭环 | 3–5 天 | 叙事价值最高；必须先有 CaptureEvent 才讲得圆 |
| 4 | ③ D2 多机位并行子代理 | O1 批次 | 3–5 天 | 需 O1 调度语义做基础，且产出上下文工程指标 |

**独立性说明**：①② 可在当前阶段（S1 已完成、D1-1 待办）**并行插入**，不阻塞 D1 主线的推进；③④ 须等待各自前置批次。

6. **是否新增 ADR 记录多智能体的引入理由**？（建议：必要，否则与路线图第 3 节"不做多 Agent"产生文本冲突）

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| MCP 协议版本演进 | 适配层需跟随更新 | 适配层独立成包，隔离协议细节 |
| 外部 Server 不可控 | 稳定性与安全风险 | 默认只接受只读工具；超时降级；可一键摘除 |
| 多 Agent 成本失控 | token 消耗成倍增长 | 硬性轮次上限 + 成本记录 + 配额账本联动 |
| 与"不做多 Agent"原则冲突 | 文档一致性问题 | 以 ADR 记录例外理由，并限定适用范围 |
| 演示效果依赖真实数据 | 无真实闭环时难展示 | 方向④排期在 E1 之后，避免"无米之炊" |
| 指标数据不完整 | 无法支撑"量化"叙事 | 每个方向均要求产出可测量数据并写入记录 |

## 10. 与求职叙事的衔接（备注）

本方案四个方向各自产出一类可量化证据，用于弥补当前项目"缺少指标"的短板：

| 方向 | 可产出的量化证据 |
|---|---|
| ① MCP Server | 工具 schema 一致性检查数、可被外部客户端列举的工具数 |
| ② MCP Client | 动态注册工具数、Server 故障降级成功率 |
| ③ 并行子代理 | 上下文 token 对比、端到端延迟对比、字段错配率 |
| ④ 双角色对抗 | 归因准确率、归因类别覆盖率、token 成本 |

**说明**：上述数据用于真实呈现项目能力边界，**不得在缺少统计样本时包装为精确概率**（遵循路线图第 3 节既有约束）。
