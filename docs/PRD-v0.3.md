# LightTrail（光迹）产品需求

> 需求修订：2026-10-06。保留原文件名与需求编号，版本为 v0.5。
> 本文定义用户问题和验收目标；当前能力见 [FEATURES](FEATURES.md)，执行顺序见 [路线图](AGENT-ROADMAP.md)。原件见 [归档](archive/audit-20261006/docs/PRD-v0.3.md)。

## 1. 产品目标

光迹帮助摄影爱好者把数据变成拍摄行动：是否出门、何时到达、去哪个机位、带什么器材、采用什么初始参数，以及条件变化时如何调整。长期沿“灵感 → 规划 → 决策 → 复盘”组织能力，个性化记忆与可核查依据贯穿全程。求职与开源目标不能代替用户效果验收。

竞品调研用于形成假设；“市场空白”“某工具精度更高”等结论未经本次独立外部核实，不作为已证实事实。保留已有领域工具和单体系统，是否引入新的主要架构另行决策。

## 2. 首个验收场景与范围

**小北已确认首个场景：“今晚火烧云是否值得去”。** 用户知道一个或几个收藏机位，希望结合剩余时间、可用器材和可靠天气，决定是否出发，并在刷新后继续看原来的计划。

建议首轮试用面向本地单用户、已有收藏机位的摄影爱好者。这是便于检验核心价值的范围建议，尚不等于小北确认最终发布形态。陌生地点发现、多机位赶场、自动提醒和公开多用户服务保留为未来范围。

首个场景验收：

1. 输入机位、题材、日期、出行耗时和必要偏好；缺少必要信息时明确询问。
2. 显示行动结论、到达与拍摄窗口、已有器材下的初始参数和失败预案。
3. 每条关键依据能核对来源、目标地点/时间、采集时间和有效范围；缺失值保持缺失。
4. 天气或太阳窗口不可用时，可以返回“数据不足，暂不能建议出发”，并说明补充什么或何时重查。不能把工具失败包装成高置信度建议。
5. 刷新、关闭后重开能够恢复原决策和计划；过期结果提示过期，重新查询不会悄悄改写原计划。
6. 用户可记录“去了/没去、是否看到、结果如何”，未来经确认沉淀经验。首轮无需先建设完整作品管理系统。

“值得赌一把”是结合机会成本的行动建议，不是天气事件概率。没有校准数据，不展示貌似统计置信区间的百分比。远期天气仅供趋势参考；近 1–3 天也必须按实际数据完整度与有效期判断，不能仅凭距离今日较近就认定可靠。

#### D2 地图与 D4 照片的验收边界（2026-09-30 补充）

- 地图仅使用用户明确保存且坐标系已知的机位；WGS84、GCJ-02、BD-09 不得混画。接高德前必须核对转换、许可、配额、Key 管理和精确坐标外发告知；未完成时显示机位列表与“地图不可用”的原因，不用虚构底图或路线填空。
- 地图标记与结构化 `SpotPlan` 的机位 ID/坐标一致；赶场线段与路线结果的顺序、交通方式、`provider`、采集时间及降级原因一致。移动端仍可通过文字列表完成规划；离线回放不依赖第三方地图服务。
- D4 预览在浏览器当前页生命周期内有效；换图或离开页面释放临时 URL。预览、上传分析、EXIF/GPS 提取、CaptureEvent 照片引用与原图长期保存是不同动作，后两项仍按 E1 的用户告知和确认执行。

## 5. 决策地基

### 5.1 M1 — 个性化记忆

**定位**：让决策「越用越懂用户」。记忆分四层：

| 层次     | 内容                         | 生命周期 | 存储             |
| -------- | ---------------------------- | -------- | ---------------- |
| 短期记忆 | 当前对话上下文               | 会话内   | 会话内上下文   |
| 用户档案 | 器材、偏好、常拍点、技能水平 | 长期稳定 | JSON 文件        |
| 事件记忆 | 拍摄记录、经验教训、纠错反馈 | 长期增长 | JSON/SQLite      |
| 用户语义经验 | 从用户事件提炼的偏好与经验 | 长期     | 本地语义存储     |

全局摄影知识与用户记忆严格分离：机型规格、规则和教材摘要属于全局只读 `knowledge/`；用户档案、事件和经验按 `user_id` 隔离。

#### M1.1 记忆写入

| 编号    | 需求                   | 范围 | 说明                                                                             |
| ------- | ---------------------- | ------ | -------------------------------------------------------------------------------- |
| M1.1-01 | 用户档案手动配置       | 范围保留 | 提供 profile 文件，用户填写器材/偏好/常拍点。                                    |
| M1.1-02 | 对话自动抽取（实验性） | 范围保留 | Agent 从对话中识别「新事实」（换镜头、新偏好、纠错），自动写回档案。核心研究点。 |
| M1.1-03 | 记忆冲突与更新         | 范围保留 | 新旧记忆冲突时（换镜头）更新而非追加；过期记忆标记。                             |
| M1.1-04 | 通勤 / 常驻画像       | 范围保留 | 支持两种位置画像：① 常驻地点（住所、工作地及其工作时间）；② 固定远距离通勤（住杨浦、工作在安亭这类跨区——晚霞时段人在工作地，赶不回常驻机位）。决策地点**默认按当前所在地**而非记忆常驻地。字段级 schema 以当前架构基线与契约为准。 |
| M1.1-05 | 事件记忆确认后记录 | 范围保留 | 一次拍摄以稳定引用关联计划、实际执行、照片、复盘和数据快照；完整 CaptureEvent 模型与迁移另行评审。只有用户明确确认后才写入长期记忆；生成计划或上传照片不等同于实际拍摄。精确坐标、EXIF 与照片遵循本地优先和最小化存储。 |

#### M1.1.x 事件记忆字段语义（D2.3-07 复拍提醒的数据前提）

| 字段 | 说明 | 来源 |
| ------- | ------- | ------- |
| 时间戳 + 位置 | 任务必要精度；精确坐标可选，授权后采集，不默认记录住所 | 用户确认 / 授权定位 |
| 题材 + 次数统计 | 朝霞 / 晚霞 / 银河等，按年累计 | 事件表聚合 |
| 天气/天象快照 | 云量、火烧云评分、月相、能见度 | 工具结果落库（sunset_glow_score 等） |
| 器材与参数 | 机身 / 镜头 / 曝光组合 | EXIF（D4-02）联动 |
| 成果评价（可选） | 出片率 / 满意度的用户反馈 | 用户标记 |

## 7. 非功能需求

| 编号 | 要求与验收边界 |
|---|---|
| NF-01 | 等待过程可见、可取消、可重试；响应时间按场景测量。旧 10/15/30 秒为目标，未实测达标，不作为当前承诺。 |
| NF-02 | LLM_CONCURRENCY 为唯一并发配置；取消等待不得丢失许可。默认 4；ECNU 实际联调建议配置为 1。 |
| NF-03 | 工具与整轮请求具有明确超时和失败输出；旧统一 10 秒未实现。 |
| NF-04 | 控制档案、召回和历史上下文预算；自动摘要要求保留，尚未实现。 |
| NF-05 | 可重试错误有有限重试、清楚的总预算；SDK 与适配层重试不能叠加成隐形费用。 |
| NF-06 | 工具错误可隔离，但缺失关键数据必须影响决策资格。 |
| NF-07 | 验证类型、数值范围、日期时区、身份与文件边界，不能只验证 JSON 形状。 |
| NF-08 | 配置缺失可定位，敏感值不出现在错误、repr、日志或页面。 |
| NF-09 | 内部新增工具不改引擎核心；外部 MCP 工具接入属于另行提案。 |
| NF-10 | 模型选择经过能力路由；切换模型必须验证能力、扩展参数与计价配置。 |
| NF-11 | 数据源职责可替换；预留端口与实际接线分别验收。 |
| NF-12 | 支持裁切系数；规格补全按生产装配验证，不能以独立 catalog 测试代替。 |
| NF-13 | 密钥留在授权配置环境，禁止进入源码、用户上下文、repr 与脱敏后的 trace。 |
| NF-14 | 默认本地存储，并明确请求外传路径、保留期限与删除方式。 |
| NF-15 | 上下文仅包含当前任务必要信息；照片、EXIF、位置发送前有可理解的提示。 |
| NF-16 | 预报具有地点、时区、有效期与缺失标记；远期仅趋势，过期不可冒充今晚依据。 |

## 8. 验收与变更

工程回归、合成流程、真实服务联调、用户场景验收是四种证据，应分别记录。核心产品定位、重大架构、真实数据外发、费用和发布由小北确认；普通文档纠错、离线审查与已授权普通批次无需反复确认。

完整历史动机、旧优先级与范围修订见归档。新增决定记录决策依据与适用范围，不把 Agent 推断写成“用户已确认”。
